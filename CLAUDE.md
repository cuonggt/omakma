# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Omakma is an opinionated macOS developer environment bootstrapper (macOS Sonoma 14.5+), inspired by [Omakub](https://github.com/basecamp/omakub). It automates turning a fresh macOS installation into a fully-configured web development system via a single command. The entire codebase is pure Bash shell scripts (over 130 of them).

## Architecture

**Installation flow:** `boot.sh` → `install.sh` → `install/terminal.sh` + `install/desktop.sh`

- `boot.sh` — Entry point (run via curl). Installs Xcode CLT, clones repo to `~/.local/share/omakma`, sources `install/pin-to-release.sh` to pick the version, runs `install.sh`. Its first two steps are the functions `install_xcode_clt` and `clone_omakma`, and sourcing it with `$OMAKMA_BOOT_DEFINE_ONLY` set defines them without running anything — which is how `test/boot-steps.sh` reaches them, since they run before the repository exists and so cannot live in it. `$OMAKMA_CLONE_URL` and `$OMAKMA_CLONE_PATH` exist so a test can clone a local repository into a sandbox. The usual "am I being sourced" check is no help: `bash < <(curl ...)` feeds the script in on stdin, so `$0` is bash and `BASH_SOURCE` is empty
- `install/pin-to-release.sh` — Decides what a fresh install gets: the most recent tag reachable from `origin/master`, or `$OMAKMA_REF`. It moves `master` back to the tag with `git reset` rather than checking the tag out, because a detached HEAD leaves `omakma update`'s `git pull` with nothing to follow and no fix would ever reach the machine again. So installs are pinned and updates are not
- `install.sh` — Main orchestrator. Installs Homebrew, sources `defaults/bash/functions`, runs `install/preflight.sh` and the first-run choices via `gum`, then sources the terminal and desktop installers
- `install/terminal/` — Individual installer scripts for CLI tools, languages, and databases
- `install/desktop/` — Individual installer scripts for GUI applications
- `uninstall/` — Mirrors `install/` one-for-one. Each script removes a package and the config its installer put in place, and is meant to be safe to re-run when the app is already gone. **Largely unverified.** Eight of the 44 — alacritty, fastfetch, ghostty, iterm2, neovim, sublime, vscode and zellij — have tests covering which files they delete. The other 36 were written and reviewed as a batch and merged unexercised, and `uninstall/desktop/app-vscode.sh` removes a file with `sudo rm -f`. No uninstaller has ever actually removed anything: `test/` stubs every `brew` call and runs against a throwaway `HOME`, so a green build shows that a script deletes the right config, never that it uninstalls the package. Exercise `omakma uninstall` on a machine you can afford to break before trusting one
- `migrations/` — One-off fixes for machines that are already installed (see below)
- `bin/omakma` — Post-install runtime command providing an interactive menu
- `bin/omakma-sub/` — Sub-commands: `menu.sh`, `theme.sh`, `font.sh`, `font-size.sh`, `install.sh`, `uninstall.sh`, `update.sh`, `migrate.sh`, `dev-add-migration.sh`. `menu.sh` shifts off the sub-command name and forwards the rest, so a sub-command reads its own arguments from `$1`

**`install/terminal.sh` and `install/desktop.sh` glob `*.sh` in their own directory only.** Scripts under `optional/` and `required/` are not picked up automatically — they run only where something sources them explicitly (the first-run choices, or `omakma install`). Putting a script in `optional/` is how it gets excluded from a default install.

**Migrations:** A fix made inside an installer only ever reaches machines set up after it. When a change needs to reach existing installs too, add a migration with `omakma dev-add-migration <slug>`, which scaffolds `migrations/<unix-timestamp>_<slug>.sh`. `omakma update` sources each one at most once per machine, recording success as an empty marker under `$OMAKMA_STATE_HOME/migrations/` (`~/.local/state/omakma` by default). `install/preflight.sh` pre-touches every marker on a fresh install, so historical fixes never run on a clean machine. A migration that fails stops the run, names itself, and makes `omakma update` exit non-zero.

A migration should not simply re-source its installer. Installers are written for fresh machines and can be destructive on one that is already set up — `install/desktop/set-dock.sh`, for instance, wipes the Dock with `defaults write com.apple.dock persistent-apps -array`, which no migration should do to someone who has arranged theirs. Patch narrowly instead, and read the wanted values out of `configs/` so the migration and the installer cannot drift apart.

**Theme system:** 7 themes (default, catppuccin, nord, everforest, rose-pine, ristretto, solarized) in `themes/`. Each theme directory contains config files for alacritty, ghostty, vscode, sublime, neovim, and zellij. Theme switching is unified via `bin/omakma-sub/theme.sh`.

**Configuration files:** `configs/` contains dotfiles and settings (zshrc, gitconfig, vscode.json, alacritty/, neovim/, sublime/). `defaults/bash/` contains shell aliases, prompt, and init scripts, plus the shared installer helpers in `functions`.

## Key Conventions

- **Target bash 3.2.** macOS ships `/bin/bash` 3.2.57, so no `mapfile`, no associative arrays, no `${var^^}`. ShellCheck assumes a modern bash and will suggest otherwise — do not take that advice.
- **Installers, sub-commands, and migrations are sourced, not executed.** Stopping early therefore means `return N 2>/dev/null || exit N`; the `exit` half keeps a script usable when run directly, which is how these get tested.
- Use the helpers in `defaults/bash/functions` rather than calling `brew` or `cp` directly. Installing: `app_installed`, `app_install` (cask with an app bundle), `brew_app_install` (formula with an app bundle), `brew_install` (CLI formula), `cask_install` (cask with no app bundle). Removing: `app_uninstall`, `brew_app_uninstall`, `untap_if_unused`, `remove_installed_config`, `remove_installed_clone`, `remove_empty_dir`, `restore_config_backup`. A clone cannot be matched by content, so `remove_installed_clone` decides ownership from the remote url instead. An uninstall helper treats a package that is not installed as nothing to do rather than a failure, which is what keeps these scripts safe to re-run, and records a removal that genuinely fails through `uninstall_failed` instead of swallowing it. `uninstall_failed` returns non-zero, so an uninstaller with anything to do after the removal must stop on it — `app_uninstall x || return 1 2>/dev/null || exit 1`. Stripping the config of an app that is still installed is worse than not uninstalling it: the app is left working but unconfigured, and the config cannot be put back. Keeping the machine awake: `keep_awake` and `let_sleep`, which stop the caffeinate from an EXIT trap as well as explicitly, so an abort cannot leave it running. Switching theme or font: `edit_config` to rewrite lines in a config file and `update_config` to put a theme or font file in, both of which do nothing when the app's config is not there — `omakma theme` used to fail on every file belonging to an app the user had uninstalled. `edit_config`'s expressions are GNU sed's, and it takes GNU sed under either name (`gsed` on macOS, `sed` on a CI runner) rather than falling back to BSD sed, which would read the expression as `-i`'s backup suffix and mangle the file. Config: `backup_config` before changing a file in place, and `copy_config` for any file the user may already own — it keeps the original as `<file>.bak`, never overwrites an existing backup, and writes no backup when the file already matches what is replacing it.
- **Never let a failure look like a success.** `app_uninstall` and `brew_app_uninstall` used to end in `|| true` with stderr discarded, so every uninstaller returned 0 and `omakma uninstall` showed "Uninstall completed!" even when the app was still installed and Homebrew had explained why. Failures are recorded and named; `report_failed_uninstalls` prints them, and the menu does not clear the screen when there is something to read. `bin/omakma-sub/install.sh` had the same bug for the same reason — the install helpers return 0 when a package is skipped, so its `&&` chain never saw a failure — and both dispatches now check the failure list rather than an exit status. Neither may gate a "completed!" message on whether the sourced script returned 0.
- **A package Homebrew will not hand over is not a fatal error.** The install helpers record it through `install_unavailable`, say so, and carry on; `report_failed_installs` names everything skipped before the reboot prompt. Without this, one cask disabled upstream took the rest of the install with it, since `install.sh` runs under `set -e` and both `install/terminal.sh` and `install/desktop.sh` source their installers in a bare loop. Only the `brew install` is tolerated — every other failure still stops the run. A download that fails records through `download_failed`, and something that arrived but could not be set up through `setup_failed`; the distinction is only in the message, which is the point, since reporting a failed `valet install` as a failed download sends the user to look at their network. The Composer bootstrap in `install/terminal/select-dev-language.sh` is the worked example of why these exist: it fetched the installer with `php -r "copy(...)"`, which exits 0 and writes no file when the download fails, so the next line ran php against a file that was not there and ended the run before `install/desktop.sh` — on the default path, since PHP is preselected. It now downloads to a temp directory, checks the installer against the checksum Composer publishes on a separate host before running it, and passes `--install-dir` so the phar never lands in whatever directory the install was started from. The one deliberate exception is `install/terminal/required/app-gum.sh`: `gum` drives the first-run choices and both menus, so there is nothing to carry on with without it.
- An installer that taps (`brew tap x/y`, or a tap-qualified `brew install x/y/z`) needs its tap added to `install/trust-taps.sh`, or a fresh install stops on Homebrew's trust prompt. Its uninstaller should give the tap back with `untap_if_unused`, which only untaps while nothing is installed from it — `brew untap` on a tap that still has packages offers to uninstall them and prompts while doing it, so the guard is what keeps an uninstaller from taking unrelated packages with it. A tap more than one thing installs from, like `shivammathur/php`, is never passed: `omakma install` installs PHP versions from it, so it outlives any single app.
- Every `install/**/app-*.sh` should have a matching `uninstall/**/app-*.sh`, with the exception of `install/terminal/required/`: `gum` drives the uninstaller's own UI, so there is deliberately no way to remove it.
- First-run choices are exported as `OMAKMA_FIRST_RUN_*` and consumed by the `select-*.sh` installers. Test whether the variable is **set** (`${VAR+set}`), not whether it is non-empty: an empty value means the user chose nothing, and reading that as "never asked" produces a second prompt partway through the install.
- The main `install.sh` uses `set -e` for fail-fast behavior; most other scripts are sourced from it or run independently without it
- Homebrew is the primary package manager (`brew install` / `brew install --cask`)
- Interactive prompts use `gum` (text UI framework, installed as a required dependency)
- Language versions are managed via `mise` (not asdf)
- The install path is `$OMAKMA_PATH` (`~/.local/share/omakma`)

## Code Style

- Shell scripts: 2-space indentation, UTF-8, LF line endings (see `.editorconfig`)
- No build system. Most behavioral changes are verified by running the scripts; config handling is the exception and has tests (see below)

## Tests

`test/run.sh` exercises how installers and uninstallers treat config under the user's home. That is the only part of the codebase with automated coverage — everything else is still verified by running the scripts by hand.

```
test/run.sh            # every case file
test/run.sh alacritty  # just test/app-alacritty.sh
```

It is safe to run on a machine you care about: every case gets a throwaway `HOME` under `$TMPDIR`, every `brew` call is stubbed, and nothing reaches the network. `test/helpers.sh` refuses a `HOME` outside its sandbox, because these cases delete config directories and a path that escaped would take the real ones with it. CI runs the suite on every push and pull request to master (`.github/workflows/test.yml`). A run that fails re-lists every failed assertion at the end, each with the case file it came from, and prints the `test/run.sh` command that runs just those files again — a full run is over five hundred lines, and a truncated CI log once left a 229/1 result with nothing to diagnose.

One case file per app, `test/app-<name>.sh`, plus `test/helpers-<name>.sh` for the shared helpers in `defaults/bash/functions`. `run.sh` sources every `*.sh` in `test/` except itself, `lint.sh` and `helpers.sh`, so a case file cannot escape by not matching a name prefix. `run_script` blocks `sudo`, `brew`, `code`, `curl`, `wget`, `git clone` and the rest of what an installer reaches for, so sourcing a real installer cannot touch the machine. Stub whatever a case depends on rather than letting it read the host: a suite that passed on macOS and failed on CI has three times turned out to be reading what happened to be installed there — `gsed` versus `sed`, `wget` being present, `nvim` being on PATH — stubbing the install helpers alone is not enough, as `app-vscode.sh` will happily `sudo ln -fs` into `/usr/local/bin` and run 33 `code --install-extension` calls against your own editor. They are sourced by `run.sh` so the pass/fail counters accumulate, which means they are not runnable on their own. `OMAKMA_PATH` is pinned to the checkout the tests live in and deliberately ignores any value the shell exports — `defaults/bash/shell` exports it as `~/.local/share/omakma`, so honouring that would exercise the installed copy instead of the code under test. Alacritty and Ghostty run their real installers, since those only copy files; Neovim, fastfetch and zellij build the installed state by hand instead, because `install/terminal/app-neovim.sh` clones LazyVim over the network. Add a case file alongside any uninstaller you fix.

## ShellCheck

ShellCheck runs in CI (`.github/workflows/shellcheck.yml`) on every push and pull request to master, and any finding fails the build. Run it before pushing:

```
test/lint.sh
```

`test/lint.sh` is the one definition of what gets linted, so CI and this file cannot drift apart. It covers every `*.sh`, plus the bash that carries no extension: `bin/omakma`, the shipped `configs/bashrc`, and the helpers under `defaults/bash/`. That last directory is globbed rather than listed, so a new helper cannot escape the linter by being new — which is how `defaults/bash/functions`, the file every installer depends on, went unchecked for as long as the pattern was `*.sh` alone. Left out on purpose: `defaults/bash/inputrc` and `configs/inputrc` are readline config rather than shell, and `configs/zshrc` is zsh, which ShellCheck cannot check.

`.shellcheckrc` holds the repo-wide exemptions that follow from everything being sourced (SC1090, SC1091, SC2034, SC2154, SC2317, SC2329) and sets `shell=bash` so files without a shebang are still checked as bash. Exemptions that apply to the whole codebase belong there, with a comment explaining why, rather than as inline `# shellcheck disable=` comments repeated at each site.
